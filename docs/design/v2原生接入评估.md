# v2 原生深度接入评估（提案）

状态：**架构评估，未实现**
范围：`src/api/*`、`src/types/api/*`、`src/api/v2/*`、`src/api/clientFacade.ts`、`src/api/sdk.ts`、`src/hooks/useGlobalEvents.ts`、`src/api/events.ts`

---

## 一、问题背景

### 1.1 现象

OpenCodeUI 需要同时连 opencode v1 与 v2 两类后端。当前架构里**前端整体按 v1 SDK（`@opencode-ai/sdk`）的数据形状编写**，连 v2 后端时通过一层 facade（`src/api/clientFacade.ts`，538 行）+ `src/api/v2/*` 适配器把 v2 响应硬转回 v1 形状。v1/v2 契约差异巨大，导致：

- 每发现一处差异就打一个 `adapt` 补丁，补丁越补越碎。
- 同类问题换着形式反复出现（`text/html` 崩溃、`branch.trim`、`localeCompare`、模型列表空、命令面板空、对话无响应…）。
- 维护成本高、排查路径绕。

用户反馈：**项目太乱，各种适配问题**。

### 1.2 关键结论（先给判断）

**v2 本身没有功能缺口。** v2 有完整、成熟的第一方 HTTP + SSE 协议，官方客户端 `@opencode/client`（已装 2.0.28）覆盖前端全部需求：session/message/agent/tool/config/model/provider/file/vcs/worktree/pty/command/skill/permission/form/project/location/event…一应俱全，事件流走 `/api/event` SSE。

乱的根源在**适配层**，不在 v2。要根治，方向是让 **v2 成为第一公民**，前端直接用 `@opencode/client` 原生形状，删掉 v1→v2 的 facade 适配层。

## 二、现状依赖面量化

### 2.1 前端绑定 v1 形状的规模

| 维度 | 数值 |
|---|---|
| 调用 `getSDKClient()` 的 api 模块 | 20 个 |
| 引用 `@opencode-ai/sdk` 的文件 | 27 个 |
| `src/types/api/*`（UI 层类型定义） | 17 个文件 |
| v1 SDK 导出类型数 | ~1080 |
| v2 client 导出类型数 | ~403 |
| facade 适配层 | `clientFacade.ts` 538 行 + `src/api/v2/*` 6 文件 |

### 2.2 现有 v2 适配点（即 v1→v2 的全部形状差异）

`src/api/v2/*` 已处理的差异（代表 v1/v2 差异全集的一个子集）：

- **session**：`adaptSession`（directory↔location 等）、`adaptDataList`/`adaptEnvelope` 信封结构
- **message**：`adaptMessage`/`adaptMessagePage`——v1 Part 体系 ↔ v2 消息/part 结构
- **entities**：`adaptPermission`/`adaptAgent`/`adaptPty`/`adaptFileNode`/`adaptProviders`/`adaptSkill`/`adaptMcpStatus`/`adaptModelToProviderEntry`
- **事件流**：`v2EventToGlobalEvent`——v2 事件类型 → v1 `EventTypes`（无 message.updated 等 case）

### 2.3 前端类型系统绑定

`src/types/api/*`（Session/Message/Part/Agent/…）**直接 import v1 SDK 的 `@opencode-ai/sdk/dist/v2/client` 类型**。这意味着改造不仅是换 API 调用，UI 层消费的数据类型也要整体迁移。

## 三、两条路线对比

### A. 继续打补丁（现状）

- **做法**：保持 v1 形状为前端唯一契约，持续补 facade 适配。
- **优点**：见效快、风险低、无需动 UI 层类型。
- **缺点**：兼容性摩擦是持续的，永远"补了这处漏那处"，正是当前乱象的来源。

### B. 原生深度接入 v2（根治）

- **做法**：v2 成为第一公民，前端直接用 `@opencode/client` 原生类型与调用，删除 facade 适配层。
- **优点**：根治适配问题；v2 是 opencode 的当前主线，长期最稳。
- **缺点**：**大改造**。20 个 api 模块 + 17 个类型文件 + UI 消费层都要迁到 v2 形状；v1 后端仍需保留一套（或降级为只读/部分支持）。

---

## 四、原生接入 v2 的改造方案

### 4.1 目标架构

```
前端 api 模块 ──► getSDKClient()（v2 时返回 @opencode/client 原生）
                 │
                 └── 直接消费 v2 原生类型，无 adapt 层
```

- 移除：`clientFacade.ts` 的 v2 分支、`src/api/v2/adapt.ts`/`entities.ts`/`message.ts`/`session.ts` 的 v1 适配。
- 保留：`src/api/v2/events.ts`（事件流映射，但改为映射到前端自己的内部事件模型，而非 v1 EventTypes）。
- 核心：**前端建立自己的领域类型（DTA）**，不再直接依赖 v1 或 v2 的 SDK 形状；每个 api 模块返回 DTA，由一层薄的"v2 原生 → DTA"映射承担，v1 后端复用同一 DTA（用 v1 的映射）。

### 4.2 关键设计决策

1. **引入领域类型层（Domain Types）**：`src/types/domain/*` 定义前端真正需要的数据模型（Session、Message、Part、Agent、Model…），UI 只依赖这层。v1/v2 各自提供映射器。这是"原生接入"与"继续打补丁"的本质区别——把适配从"散落的 adapt 函数"收敛为"每代一个映射器"。

2. **事件模型独立**：前端自己的事件类型（如 `ChatEvent`），`v2EventToGlobalEvent` 改为映射到 DTA 事件，不依赖 v1 `EventTypes`。

3. **API 网关统一**：`getSDKClient()` 返回一个统一的 `AppClient` 接口（DTA 形状），内部按 apiVersion 分派到 v1/v2 实现。删除 `createV2Facade`。

### 4.3 分阶段实施

| 阶段 | 内容 | 交付物 |
|---|---|---|
| **P0 诊断** | 修复当前"对话无响应/无法归档" | 具体 bug 修复（见下节） |
| **P1 事件/消息流** | 先迁事件总线 + 消息渲染到 DTA | 对话可正常流式 |
| **P2 会话/侧栏** | session 列表/状态/新建迁移 | 侧栏正常 |
| **P3 能力模块** | 逐个迁移 config/model/mcp/file/vcs/worktree/pty/command/skill/permission | 各功能正常 |
| **P4 清理** | 删除 facade 与 v1 适配器 | 架构收敛 |

每阶段独立可交付、可回归验证，避免一次性大改导致 UI 全面回归。

## 六、附：当前"对话无响应/无法归档"诊断线索

（P0 修复参考，尚未定案）

实测 v2 prompt 后 `/api/event` 推送的事件序列（工作主机，opencode 2.0.28）：

```
session.inbox.enqueued → project.updated → session.execution.started
→ session.instructions.updated → session.inbox.delivered
→ session.step.started → session.reasoning.started
→ session.reasoning.delta → session.text.started → session.text.delta
→ session.tool.input.started → ... → session.text.ended
→ session.step.ended → session.usage.updated
```

**未出现 v1 依赖的 `message.updated`/`message.created`**。而前端渲染 assistant 消息依赖 `onMessageUpdated`（`EventTypes.MESSAGE_UPDATED`）先创建消息骨架，再用 delta 填充。当前 `v2EventToGlobalEvent` 也没有 `message.updated` 的 case。

疑似根因：**v2 用 `session.*` 事件驱动消息流，前端却等 `message.*` 事件建骨架**，导致发出后 UI 一直转圈看不到回复。需进一步确认前端消息渲染的建骨架路径，再定修复方案（这属于 P1 迁移的先行项）。
