# 数据同步层设计（提案）

状态：**设计提案，未实现**
范围：`src/store`、`src/hooks/useGlobalEvents.ts`、`src/api/events.ts`、`src/api/preferencesSync*.ts`、`src/utils/perServerStorage.ts`

---

## 一、为什么要做

### 1.1 现象

后台会话的「正在运行 / 已结束 / 未读」只有在点开该会话后才正确同步。这不是孤例，而是长期反复出现的一类问题的最新一次表现。

### 1.2 直接根因（本次 bug）

1. 状态对账的范围被目录切碎：`fetchActiveScopeData`（`src/hooks/useGlobalEvents.ts:221`）按活动目录逐个查 `/session/status?directory=X`，而该接口按 directory 过滤（实测：不同目录返回不同集合）。
2. 合并只增不删：首次连接走 `initialize` 整表替换（`src/store/activeSessionStore.ts:192`），但重连/目录变化走 `mergeStatusRefresh`（`:204`），只能删「payload 里显式为 idle」的条目，范围查询返回不到的目录的陈旧 busy 永远清不掉。
3. 整台替换只在回前台触发：`replaceServerStatus`（`:220`）只被 `visibilitychange` 调用（`useGlobalEvents.ts:1023`），重连和侧栏展开都不会触发。
4. 点开会话把该目录写入活动目录集合（`src/App.tsx:253` → `collectActiveDirectoriesByServer` `src/utils/activeScope.ts:23`），触发一次范围刷新，于是表现为「点一下才对」。

### 1.3 结构根因

「同步」这件事没有归属，被拆成四个互不感知的面：

| 面 | 位置 | 职责 |
|---|---|---|
| SSE 事件总线 | `src/api/events.ts` + `src/hooks/useGlobalEvents.ts` | 服务端权威状态（消息/状态/权限/子会话） |
| 跨端偏好同步 | `src/api/preferencesSync.ts` + `preferencesSyncEngine.ts` | localStorage 偏好，走 API Monitor 账号 |
| per-server 存储通知 | `src/utils/perServerStorage.ts` | 存储写入后的重读 |
| store 内部对账 | 各 store 自行实现 | 快照/增量合并 |

历史上每次只统一其中一块（`cabf9fa3` 统一 MessageStore、`feca04b6` 统一 Rust bridge、`17776882` 解耦 active/notification、`32bf77b3` 引入 sessionActivityStore）。**每当新增一个维度（多服务器、跨端、分屏、移动端），同一批问题就换一种形式重现。**

### 1.4 高频改动佐证

`git log --all` 统计（含上游引用分支）：`SessionList.tsx` 73 次、`FolderRecentList.tsx` 69 次、`useGlobalEvents.ts` 65 次、`messageStore.ts` 59 次、`events.ts` 44 次。改动 `src/store/` 的提交 236 个。同步相关关键词命中：SSE/reconnect 127、busy/idle/status 104、merge/dedup 110、sync 82、multi-server 80、stale/race 55、unread/notification 48。

### 1.5 多端不一致（桌面端 vs 网页端）

实测现象：同一账号在两台设备打开同一 opencode 后端，侧栏显示不一致 —— 某会话在一端是「刚刚」，另一端是「5 分钟」；未读点、列表顺序、项目时间戳对不上。

根因不是单一 bug，而是**「同步」这个词下混了三类语义完全不同的数据**：

| 类别 | 例子 | 权威源 | 跨端语义 | 现状 |
|---|---|---|---|---|
| A 服务端权威 | 消息、会话列表、busy/idle、权限、todo | opencode 后端 | 各端独立从同一后端派生 | 各端独立 SSE + 快照 |
| B 账号偏好 | 主题、模型、置顶、已保存项目 | API Monitor 账号 | 显式跨端同步 | preferencesSync |
| C 设备本地派生 | 未读/已读、项目最后使用时间、列表排序锚点、侧栏开合、草稿 | 本机 | 当前不共享（部分有意） | localStorage / 内存 |

截图里的「4分 vs 5分」属于 C 类：`useProjectLastUsedAt`（`src/hooks/useProjectLastUsedAt.ts:18`）每端各自查 `/session?directory=` 并缓存 60s，不是共享数据，两端天然会漂移。未读点同理：`opencode:notifications` 被显式排除跨端同步（`src/api/preferencesSync.ts:153`），一端点开不会清另一端的未读。

### 1.6 服务端有序事件流：可检测缺口，但不可重放

> 本节已按 **opencode v2.2.0** 重新实测更新（旧版 `sync` 事件在当前协议里已不存在）。

当前协议里，**durable 事件自带序号信封**，不再有独立的 `sync` 事件：

```json
{"id":"evt_x","created":1793277194355,"type":"session.step.ended",
 "data":{...},
 "durable":{"aggregateID":"ses_xxx","seq":1223,"version":1}}
```

**实测结论（本机 opencode v2.2.0，抓取 554 条事件）：**

| 事实 | 实测证据 |
|---|---|
| `seq` 是 **per-aggregate（按会话）** 编号，非全局 | 同一时间流里新会话 seq 8–15、老会话 seq 29364–29365 并存；单会话抓包内 seq 连续递增无跳号 |
| 只有 durable 事件带 seq | 554 条里 `reasoning.delta`(412) / `text.delta`(67) / `usage.updated`(4) / `shell.*` 均**无** `durable`；`step.*` / `tool.*` / `inbox.*` / `execution.*` 有 |
| **`session.log?after=N` 不回放历史事件** | `after=0` / `after=4790` 都只返回 `{type:"log.synced",seq:当前水位}`，无任何历史事件 |
| `version` 是事件类型的 schema 版本，不是序号 | 同一次抓包里 `version` 取值 1/2，与 seq 无关 |

**这意味着：** 客户端可以用 `seq` **检测缺口**（跳号 → 该会话数据不可信 → 重拉快照），但**不能靠游标补发**。缺口的唯一修复手段是 HTTP 快照。

这与 Discord（RESUME 重放）、Matrix（`/sync?since`）、Gmail（`historyId` 增量）不同——那些服务端支持重放。opencode 是上游、不归本项目改，因此 A 类的补偿策略只能建立在「**seq 检测缺口 + 快照重拉**」上，而非增量续传。

**已落地**（`src/api/seqGap.ts` + `src/api/events.ts`）：

- `SeqGapTracker` 按 `(serverId, aggregateID)` 记录水位，判定 `apply` / `duplicate` / `gap`；
- 缺口事件**直接丢弃**（先写进去再被快照覆盖会让 UI 闪错内容），并通过 `onSeqGap` 通知上层；
- 上层标记该会话 stale + 通知 pane 重拉，然后 `ackSeqGap` 清空水位（否则会一直卡在 gap 上反复重拉）；
- 有界：最多跟踪 512 个 aggregate，LRU 淘汰。

### 1.7 移动端生命周期未建模

- 冷启动：A 类全是内存态（`messageStore`/`activeSessionStore`/`sessionListIndexStore` 均不持久化），必然全量重拉。
- 后台冻结：`src/api/events.ts` 有 `BACKGROUND_HEARTBEAT_TIMEOUT` / `BACKGROUND_KEEPALIVE_INTERVAL` 与 `visibilitychange` 处理，但冻结期间丢失的事件无法补，只能靠回前台重拉。
- 原生实况通知：`src/utils/liveUpdateSync.ts` 订阅 `activeSessionStore`，改其更新时机必须同步考虑。
- 弱网：退避与重试散落在各 hook（如 `useProjectLastUsedAt` 自带 3 次退避）。

### 1.8 无设备身份

全仓库无 `deviceId` / `clientId`。跨端读状态若要共享，需按设备记 lastRead 或按消息记已读，二者都需要设备标识或服务端支持。

## 三、目标与非目标

### 3.1 目标

- 每个「同步资源」用一份声明式配置描述：身份（作用域）、数据来源、合并语义、持久化。
- 引擎统一负责触发时机、竞态丢弃、在途去重、删除墓碑。
- 纯归约原语全部可单测，与 React / 网络解耦。
- 当前 bug（session-status）在新模型里是**一份声明**，而非散落多处补丁。
- 明确区分 A/B/C 三类数据的同步语义，并为 A 类接入服务端 `sync` 序号流做缺口补偿。

### 3.2 非目标

- 不合并两套同步的**传输**：偏好同步走 API Monitor 账号（`/api/aiagent/preferences`），服务端状态走各 opencode 后端 SSE。传输保持独立。
- 不做全量重写。分期迁移，每期行为等价 + 单测通过。
- 不改 UI 组件结构。
- **不自动把 C 类（设备本地派生）变成跨端共享**。C 类是否共享是产品决策，本设计只提供机制（如按设备 lastRead），不默认开启。侧栏开合、草稿等已有意排除，保持不共享。

## 四、架构总览

**薄引擎 + 声明式资源注册表**，而不是一个巨型 store。

```
   SSE 原始事件 ─┐
   SSE sync(seq)─┼─▶┌───────────────────────────────┐
   HTTP fetch  ──┼─▶│  SyncEngine                    │
   storage 变更 ─┼─▶│  - 每 server 一条订阅           │
   手动 invalidate┘  │  - sync seq 缺口检测/去重        │
                     │  - 事件按 scopeOf 路由          │
                     │  - epoch 丢弃陈旧快照           │
                     │  - microCache 在途去重          │
                     │  - 统一触发点调度               │
                     └──────────────┬────────────────┘
                                    │ 调用资源声明的 reduce
                     ┌──────────────▼────────────────┐
                     │  SyncResource<T>（声明）        │
                     │  scopeOf / fetch / events /     │
                     │  reconcile / persist            │
                     └──────────────┬────────────────┘
                                    │ 写入
                     ┌──────────────▼────────────────┐
                     │  Store（保持现有 API + hooks）  │
                     └───────────────────────────────┘
```

Store 对外接口（`useBusySessions`、`useHasUnreadCompletedNotification` 等）不变，组件几乎不动；变化在「谁来写 store、按什么语义写」。

## 五、核心概念

### 5.1 Scope（统一作用域）

全站唯一的身份合成/解析入口，替代散落的 `makeSessionKey` + 目录字符串拼接。

```ts
// src/sync/scope.ts
export interface Scope {
  serverId: string
  sessionId?: string
  directory?: string
}

export function scopeKey(scope: Scope): string   // 稳定序列化键
export function sessionScope(serverId: string, sessionId: string): Scope
export function serverScope(serverId: string): Scope
export function directoryScope(serverId: string, directory: string): Scope
export function matchesScope(a: Scope, b: Scope): boolean  // 归一化目录后比较
```

要点：
- 目录比较统一走 `normalizeForComparison`（正斜杠 + 去尾斜杠 + 小写），避免 `E:\X` 与 `e:/x` 算出两个作用域（P6 的直接来源）。
- 复合 key 的既有约定 `serverId::sessionId`（`src/utils/sessionKey.ts:16`）保留，`Scope` 是它的结构化升级，不做破坏性替换。

### 5.2 SyncResource（资源声明）

```ts
// src/sync/types.ts
export type ReconcileMode =
  | 'replace-scope'   // 每次快照整段替换该作用域（修 P5 只增不删、P9 不对账）
  | 'merge'           // 快照合并，删除靠墓碑
  | 'three-way'       // 带基线快照的三方合并（修 P4）

export interface SyncResource<T> {
  id: string
  /** 事件/实体 → 作用域。返回 null 表示不归本资源管 */
  scopeOf(raw: unknown): Scope | Scope[] | null
  /** 权威快照。signal 用于取消 */
  fetch(scope: Scope, signal: AbortSignal): Promise<T>
  /** 增量事件 → 新状态。返回 null 表示忽略该事件 */
  events?: Partial<Record<EventType, (state: T, payload: unknown) => T | null>>
  reconcile: ReconcileMode
  /** 删除墓碑：从实体/事件提取 id，供 merge 模式判定删除 */
  tombstoneOf?(entity: unknown): string | null
  /**
   * 待定事件缓冲：事件依赖的实体尚未建立时（如 delta 先于 part.updated），
   * 暂存到该实体的 pending 队列，实体建立后由引擎回放。返回 null 表示无需缓冲。
   * 解决 D5（delta 无缓冲、乱序即丢 token）。
   */
  deferIfUnresolved?(state: T, payload: unknown): { key: string; event: unknown } | null
  persist?: PersistSpec
  /** 快照 TTL；到期后下次触发会重新 fetch */
  ttlMs?: number
}
```

**`replace-scope` 的最小作用域是 server，不是全局。** D1（多服务器并发 replace 互相覆盖）的根因就是旧 `initialize` 用全局 scope（`{}` / `new Map()`）而非按 server。引擎必须保证：一次 `replace` 只影响 `scopeOf` 返回的那个 scope 下的条目，其余 scope 原样保留。`replaceServerStatus`（`activeSessionStore.ts:220`）已是正确形态，作为范式。

### 5.3 Epoch（快照世代）

每个 `(resourceId, scopeKey)` 维护一个单调递增 epoch。fetch 发起时记下 epoch，回来时若已变则丢弃（P8）。等价于 `sessionListIndexStore` 的 `expectedMembershipRevision`（`src/store/sessionListIndexStore.ts:99`）提升为通用能力。

**关键：epoch 校验由引擎内建，资源声明不能绕过。** D2 的教训是——`sessionListIndexStore.replace` 已实现版本校验，但生产调用点全都没传 `expectedMembershipRevision`，机制形同虚设。因此新设计里，`fetch` 的发起与回写都经引擎，epoch 由引擎记录与比对，资源无法选择"不校验"。这是"能力存在"与"能力被强制使用"的区别。

### 5.4 触发时机（统一调度）

引擎集中处理，各 store 不再各写一份：

| 触发 | 动作 | 修复 |
|---|---|---|
| 服务器首次连接 | 全部资源 `replace-scope` 初始化 | P2 |
| SSE 重连 | 按 `sync` seq 缺口决定：连续则只处理积压，有缺口才重拉该 aggregate | P2/P7/P8 |
| 回前台 | 服务器级资源整段对账 + seq 缺口检测 | P2 |
| 作用域集合变化（打开会话/切目录） | 仅新增作用域 fetch | P1 |
| 资源声明 `ttlMs` 到期 | 静默刷新 | P1 |
| 显式 `invalidate(resourceId, scope?)` | 精确失效 | P1 |
| storage 外部写入 | `persist` 资源重读 | P1 |

## 十、多端同步设计

三类数据（§1.5）同步语义不同，分开处理。

### 10.1 A 类：服务端权威数据（多端一致性）

A 类的多端一致性**不需要额外传输**：所有端都连同一个 opencode 后端，只要每端都能及时、完整地反映后端状态，多端自然一致。问题全在「及时」和「完整」上。

**关键改进：用服务端 `sync` 序号流检测缺口，用 HTTP 快照修复缺口。**

由于 opencode **不支持从游标重放**（§1.6 实测），不能做 Discord/Matrix 式的增量续传。可行的是「缺口检测 + 快照重拉」：

```ts
// src/sync/eventStream.ts
export interface SyncEnvelope {
  aggregateID: string          // 会话（seq 是 per-aggregate 的，实测确认）
  seq: number                  // 该 aggregate 内单调递增
  type: string                 // 'session.status' / 'message.part.updated' ...
  data: unknown
}

// 每 (serverId, aggregateID) 记录已应用的最高 seq
// 事件到达：
//   seq === last + 1  → 正常应用
//   seq <= last       → 重复，丢弃（修 P7 重复推送）
//   seq > last + 1    → 检测到缺口，该 aggregate 数据不可信 → 重拉其快照（修 P8/P2）
```

与「重连一律全量重拉」的差别：

- 网络抖动/移动端后台冻结后重连，**若各 aggregate 的 seq 连续**，说明没丢事件，只处理新事件，**零重拉**。
- **只有检测到缺口的 aggregate** 才重拉一次其快照，范围最小。
- 天然去重，缓解 P7。

**引擎侧要做的：**

1. `events.ts` 的 `isGlobalEvent` 放宽以接收 `sync` 事件，或在解析层把 `sync` 与原始事件归并（实测 `sync.syncEvent.id` 与原始事件 `payload.id` 同值，可按 `id` 配对）。
2. 引擎维护 `lastSeqByAggregate`（键 = `serverId + aggregateID`）。
3. `scopeOf` 把 `aggregateID` 映射到 `Scope`。
4. 缺口修复走该资源声明的 `fetch(scope)`（HTTP 快照），而非游标。

**冷启动的初始态一致性（避免订阅与快照竞态）：**

行业做法（Matrix/Discord）是「先取快照 + 游标，再订阅，用游标桥接间隙」。opencode 无游标，因此改为：

1. 先建 SSE 订阅并开始缓冲事件。
2. 并发拉 HTTP 快照。
3. 快照落地后，按 `seq` 丢弃比快照旧的缓冲事件，应用其余。

这样不会「订阅前的事件丢失」或「快照覆盖订阅后的新事件」。

**多端一致性验收（A 类）：** 设备 A 发消息 / 结束会话，设备 B 的侧栏在延迟上界内出现同一 busy 态、同一未读点，无需刷新或点开。这是 A 类多端一致，靠「每端都正确」实现，不靠跨端传状态。

### 10.2 B 类：账号偏好（已有机制，但有缺陷需修）

`preferencesSync` 已实现白名单 + 逐键时间戳 + 三方合并 + 墓碑（`src/api/preferencesSync.ts:601` `threeWayMergeIds`）。机制方向正确，但存在若干缺陷，其中三条影响多端正确性。

#### 缺陷 1（严重）：时间戳用本地钟，时钟偏差导致单向覆盖

`updatedAt` 全部由本地 `Date.now()` 生成（`preferencesSync.ts:903,916,947`），推送带 `lastWriteWins=1`（`:924`），服务端信任客户端时间戳。若设备 A 时钟快 5 分钟，A 写的每个键时间戳永久大于 B，**B 的改动永远被 A 顶掉**。这是跨端 LWW 的经典陷阱，与未读水位同源。

**修：** 时间戳改由服务端生成，或客户端用校准钟（`serverStore.getActiveCalibratedNow()`，`serverStore.ts:442`）。对齐「服务端权威时间」。

#### 缺陷 2（严重）：普通标量键没有删除语义

`collectLocalPreferences` 只采集「存在的键」（`:223`）。删除一个键后本地不再包含它，push 不表达删除，服务端旧值仍在，下次 pull 又写回本地（`:815-822`）。**普通键的删除无法同步，会被复活。** 只有 3 个聚合键有墓碑。

**修：** 墓碑机制扩展到标量键；或明确「删除即恢复默认」并把默认值纳入同步。对齐「墓碑 + 三方合并」。

#### 缺陷 3（严重）：对象型键是整键 LWW，会互相覆盖

`MERGE_RULES` 只覆盖 `pinned-sessions` / `saved-directories` / `pinned-messages`（`:412`）。其余键（`opencode-keybindings`、`theme-*`、`sound-settings` 等）都是整键 last-write-wins。设备 A 改主题色、设备 B 改字体，**后写者把前者一起覆盖**。

**修：** 对象型键改**字段级三方合并**，复用现有 `threeWayMerge`。对齐 VS Code Settings Sync 的字段级语义。

#### 缺陷 4（体验）：本地改动只有部分键即时上传

`startStorageSubscription` 只订阅 `subscribePerServerStorageVersion`（`preferencesSyncEngine.ts:179`），而 themeStore / layoutStore / keybindingStore / soundStore 都直接 `localStorage.setItem`，不 bump 版本。这些键只能靠 15s 轮询的指纹检测（`POLL_INTERVAL_MS = 15_000`），延迟 0–15s，与注释宣称的「本地一改立刻上传」不符。

**修：** 统一写入通知，让所有同步键的写入都 bump 版本，而非只认 `serverStorage`。

#### 缺陷 5（体验）：后台不上传

`poll()` 在 `document.visibilityState !== 'visible'` 时直接返回（`preferencesSyncEngine.ts:130`），移动端后台的改动无法上传。

**修：** `visibilitychange` 回前台补跑一次同步。

#### 缺陷 6（依赖）：`map-number` 声明未实现

类型定义了 `{ kind: 'map-number' }`（`preferencesSync.ts:402`），`MERGE_RULES` 无实例。这正是未读水位（§10.3 C3）要用的规则，需补上。 ✅ 已补实例 `opencode-read-watermarks`

#### 缺陷 7（边界）：首次同步服务端无条件胜出

`known` 基线为空时无从区分「本地默认值」与「用户改动」（`:813` 注释），服务端胜出。新设备先改设置再登录，本地改动会被服务端旧值覆盖。

**修：** 首次同步改为按戳比较，而非服务端无条件胜出。

#### 优化汇总

| 缺陷 | 优化 | 优先级 |
|---|---|---|
| 1 时钟偏差 | 时间戳改服务端生成 / 客户端校准钟 | 必须 |
| 2 删除复活 | 墓碑扩到标量键 | 必须 |
| 3 整键覆盖 | 对象键字段级三方合并 | 必须 |
| 4 即时性 | 所有同步键写入都 bump 版本 | 体验 |
| 5 后台 | 回前台补跑同步 | 体验 |
| 6 map-number | 补 `MERGE_RULES` 实例 | ✅ 已补（`opencode-read-watermarks`） |
| 7 首次同步 | 改按戳比较 | 边界 |

B 类的冲突原语（`threeWayMerge`）提取为共享纯函数后，A 类聚合资源（置顶、已保存项目）也复用同一套。

### 10.3 C 类：设备本地派生

未读/已读、项目最后使用时间、排序锚点目前各端本地派生，天然漂移。按数据性质分三种处理：

| 方案 | 机制 | 成本 | 适用 |
|---|---|---|---|
| C1 不共享（现状） | 各端独立 | 零 | 侧栏开合、草稿（有意不共享） |
| C2 派生自 A 类 | 改为从 A 类权威数据推导 | 低 | 项目最后使用时间、排序锚点 |
| C3 共享已读水位 | 同步每会话的已读时间戳，取最大值 | 中 | 未读/已读（**必须做**） |

#### C2：项目最后使用时间

`useProjectLastUsedAt`（`src/hooks/useProjectLastUsedAt.ts:18`）每端各自查 `/session?directory=` 并缓存 60s，是截图里「4分 vs 5分」漂移的来源。**改用服务端 `time.updated`**（会话列表本就带），不再各自轮询。

原则：**能派生的数据不进同步层。** 项目时间戳、列表排序都从 A 类服务端数据派生，而非跨端传输。侧栏开合、草稿保持 C1（有意不共享）。

> 注：D12（`useProjectLastUsedAt` 与锚点打架导致时间戳回退、排序跳变）与本节 C2 是同一问题的两种表现——`useProjectLastUsedAt` 的本地轮询/锚点覆盖都应被"改用服务端 `time.updated` 派生"取代。D29（大小写规范化不一致）是同一路径的实现细节。

#### C3：未读必须跨端同步（明确需求）

**需求：一台设备标为已读后，另一台设备不得再显示未读。**

**行业做法（Slack / Discord / Zulip）：** 已读状态存在**服务端**，按 `user + channel` 存一个 `last_read` 时间戳。客户端只读、只写自己的读位置，不做设备间 CRDT 合并。

**本项目对应：** 有 API Monitor 账号服务，它就是那个中心点。因此：

- **权威存在账号服务**：每 `(后端实例, 裸 sessionId)` 一个已读水位时间戳，随账号同步。
- **本地只读**：判定未读 = `notification.timestamp > watermark[sessionId]`。
- **离线写入兜底**：无网时本地先记水位，联网后按 `max` 合并上传——这是离线容忍，不是主路径。

**不采用「同步整个通知数组」。** 通知 `id` 是各端随机生成的（`notif_${Date.now()}_${random}`，`notificationStore.ts:153`），跨端对不齐；整键 last-write-wins 会重演 `7313de09` 的「已读又变未读」。

**水位模型：**

```ts
// 键：opencode-read-watermarks（账号级，随 preferencesSync 通道）
// 值：{ [后端实例 + 裸 sessionId]: 校准时间戳 }
type ReadWatermarks = Record<string, number>
```

- **判定未读**：`notification.timestamp > watermarks[key]`（取代现在的 `notification.read` 布尔）。
- **标记已读**：`watermarks[key] = max(watermarks[key], calibratedNow())`。
- **合并规则**：取最大值（单调递增，收敛型）。

为什么这个模型满足需求且风险低：

| 需求/风险 | 水位模型如何应对 |
|---|---|
| 一端已读，另一端必须已读 | 服务端存权威 + `max` 合并只会升不会降 |
| 不需要设备身份 | `max` 是收敛型，无需知道写入方（Slack 也不需要设备身份） |
| 不重演「已读又变未读」（`7313de09`） | 整键 LWW 会被旧值覆盖；水位 max 天然免疫 |
| 键跨端一致 | 用裸 sessionId（`sessionKeyToSessionId` 已有），不用随机 notif id |
| 时间跨端可比 | 用服务端校准时间（`serverStore.getActiveCalibratedNow()`，`serverStore.ts:442`） |
| 数据量 | 每会话一个时间戳，远小于同步整个通知数组 |

**必须配套的两处改动：**

1. 通知 `timestamp` 现在用本地 `Date.now()`（`notificationStore.ts:160`），与校准水位不同基准，无法比较。**通知生成时间必须改用校准时间。** 校准不可用时（`getActiveCalibratedNow` 返回 `undefined`）退回本地钟，并接受该端水位与其它端可能有偏差。
2. 通知历史本身仍不同步（`opencode:notifications` 保持排除，`preferencesSync.ts:153`）。各端各存历史，但「未读」由共享水位判定，历史里的 `read` 字段降级为本地缓存。

**同步通道**：水位是小体量 map，走 B 类 `preferencesSync` 通道。合并规则用已有的 `{ kind: 'map-number' }`（类型已声明于 `preferencesSync.ts:402`，`MERGE_RULES` 尚无实例），语义即「逐键取最大」。

**作用域**：水位按 `(后端实例, 裸 sessionId)` 存。跨端要跨 `local` 与 `aiagent:inst_x` 前缀对齐（同一后端多前缀），需要统一「后端实例身份」——见 §16 待决问题 7。

**C 类验收：** 项目时间戳两端一致（C2）；A 设备读会话后，B 设备未读点在同步延迟内消失（C3）。

## 十一、延迟、拓扑与一致性边界

### 11.1 拓扑：两条独立通道，没有中央同步服务

```
设备 A ──(opencode SSE)──▶ 主机1 的 opencode 后端 ──(opencode SSE)──▶ 设备 B
设备 A ──(API Monitor preferences SSE)──▶ 账号服务 ──▶ 设备 B
```

opencode 后端跑在每台主机上，前端只是客户端。因此：

- **A 类（会话状态/消息）没有中央同步服务。** 每台设备各自连后端，所谓「同步」其实是「两端观测同一个后端」。只有连的是同一实例才有同步可言；各连各的主机时本就该不同。
- **B/C 类（偏好、已读水位）走 API Monitor 账号通道**，是另一条独立的 SSE（`src/api/preferencesEvents.ts`）。

### 11.2 延迟是拓扑固有的，消不掉

- A 类延迟 = 每台设备到后端的网络路径。代码注释多次提到经网关隧道每次请求约 1.1s 固定往返（`src/utils/microCache.ts:9`、`src/api/session.ts:45`）；本机直连是毫秒级。桌面端直连 + 网页端走隧道时，两端天然相差约 1 秒以上。
- B/C 类多一跳账号服务：写入 → 500ms 防抖（`preferencesSyncEngine`）→ 服务端 → 对端 SSE → 对端再 GET 取值。量级几百毫秒到数秒。

### 11.3 关键区分：滞后 ≠ 错误

延迟只应造成**滞后**（暂时不一致），不应造成**永久错误**。这取决于合并语义是否收敛：

| 数据 | 合并语义 | 延迟下的行为 |
|---|---|---|
| 会话状态 | `replace-scope` + seq 缺口检测 | 滞后后收敛，不会卡住 |
| 已读水位 | `max` 单调递增 | 一端延迟只让未读多留一会儿，最终收敛，**永不回退** |
| 偏好 | 三方合并 + 时间戳 | 收敛 |

已读水位用 `max` 合并，是最抗延迟的设计：B 晚 10 秒收到水位，结果只是「未读多显示 10 秒」，不会「读了又变未读」。延迟不影响正确性。

### 11.4 会因延迟变成永久错误的两类陷阱

1. **时钟偏差**：水位若用本地钟，两端相差几分钟就会误判。必须用校准钟（`serverStore.getActiveCalibratedNow()`，基于后端 `server.connected` 时间戳）。未校准的端（离线）退回本地钟会引入偏差，需明确降级策略（待决 #5a）。
2. **非收敛合并**：整键 LWW 会因延迟与乱序导致「读了又变未读」（`7313de09`）。必须避开。

### 11.5 一致性边界（必须接受）

1. A 类一致性是**每后端**的：只有两台设备连同一 opencode 实例才谈得上同步。
2. 跨端读状态必须有账号：B/C 类走 API Monitor 账号通道，未登录即无跨端通道。
3. 后端实例身份要对齐：`local` 与 `aiagent:inst_x` 可能指向同一后端，跨端键必须用稳定实例标识（待决 #7）。

### 11.6 结论

**目标不是消灭延迟，而是：选收敛型合并（水位 max、状态 replace-scope、seq 缺口检测）、统一校准时钟、为延迟设上界（SLO）。** 延迟表现为「慢一点一致」，而非「状态错乱」。

## 十二、与成熟系统的对比

同类问题在成熟系统里有既定解法。对比后确认本设计的取舍是否合理。

| 系统 | 权威态增量 | 已读状态 | 偏好同步 | 对标本项目 |
|---|---|---|---|---|
| Discord | Gateway `session_id` + `seq`，断线 RESUME 重放 | 服务端 per user/channel ack | — | A 类 / 未读 |
| Matrix | `/sync?since=token` 增量长轮询 | 服务端 per user/room read receipt | — | A 类 / 未读 |
| Gmail | `historyId` 单调游标，`history.list` 增量 | 服务端 | — | A 类 |
| Slack | — | 服务端 per user/channel `last_read` | — | 未读 |
| VS Code / Codespaces | — | — | 中心服务 Settings Sync（非端到端） | B 类 |
| Figma / Linear | 服务端权威 + CRDT/OT 协作编辑 | — | — | （本项目无协作编辑） |

**共同模式：**

1. **权威态用可续传游标**（Discord seq / Matrix since / Gmail historyId）。
2. **已读状态中心化存服务端**，客户端只读写自己的读位置（Slack/Discord）。**不是设备间 CRDT。**
3. **能派生的不跨端同步**（derived state 不进同步层）。
4. **偏好走中心服务**（VS Code Settings Sync），不是端到端。

**本设计的取舍与理由：**

| 项 | 行业做法 | 本项目 | 差异原因 |
|---|---|---|---|
| A 类断线 | 游标重放 | **seq 检测缺口 + 快照重拉** | opencode 不重放（§1.6 实测），是上游约束 |
| A 类冷启动 | 快照+游标桥接 | 先订阅缓冲、快照落地后按 seq 丢弃旧事件 | 同上，无游标 |
| 未读 | 服务端权威 | **账号服务存权威水位 + 离线 max 兜底** | 有账号服务可用，对齐行业 |
| 项目时间 | 不适用 | **从服务端 `time.updated` 派生** | 对齐「能派生不同步」 |
| busy 态 | 短暂态 | 视作短暂态，不持久化 | 对齐 |

**结论：** 原则层面（三分法、收敛优先、幂等、派生不同步）与成熟系统一致。唯一的结构性差距是 A 类增量续传——受 opencode 上游限制，只能降级为「缺口检测 + 快照重拉」。其余均可对齐行业最佳实践。

## 十三、移动端同步设计

移动端与桌面共用同一引擎，差异在生命周期。

### 12.1 冷启动

A 类全是内存态，冷启动必然为空。策略：

1. 立即渲染（侧栏从持久化的 B/C 类偏好出骨架）。
2. 引擎对每个资源发一次 `replace-scope` 全量 fetch（现有 `firstConnect` 路径）。
3. 首个快照到达前显示 loading，不用陈旧数据冒充。

### 13.2 后台冻结 → 前台

Android/iOS WebView 后台会冻结 timer 与网络，事件丢失。策略：

1. `visibilitychange → visible` 时，用 §10.1 的 seq 缺口检测：
   - 连接仍活、seq 连续 → 只处理积压事件。
   - 有缺口 → 该 aggregate 快照重拉（opencode 不重放，见 §1.6）。
   - 连接已死 → 走重连 + 全量对账。
2. 保留现有 `replaceServerStatus` 全量对账作为兜底（`useGlobalEvents.ts:1023`）。

### 13.3 原生实况通知

`src/utils/liveUpdateSync.ts` 订阅 `activeSessionStore`，其更新时机由引擎统一后，实况通知与侧栏自动同源，消除「一个运行中一个已结束」。迁移 `activeSessionStore` 时必须回归实况通知。

### 13.4 弱网

- fetch 统一走 `microCache`（在途去重）+ 有限退避。
- seq 缺口检测天然抑制「重连风暴全量重拉」。

## 十四、期望效果（可验收）

### 14.1 单端

- 侧栏 busy/unread 与主对话区始终一致，不用点开会话。
- 重连、回前台、冷启动后 N 秒内收敛，无陈旧 busy、无残留未读。

### 14.2 多端（同一后端）

- A 发消息，B 侧栏在延迟上界内出现同一会话、同一 busy 态。
- A 结束，B 出现同一未读点。
- **A 设备读会话后，B 设备未读点在同步延迟内消失（未读跨端一致）。**
- 两端列表顺序、项目时间戳一致（C2 消除本地派生漂移）。

### 14.3 延迟上界（SLO，需实测标定）

- 本机直连：A 类两端一致 < 1s。
- 经网关隧道：A 类两端一致 < 3s。
- B/C 类（含已读水位）：< 5s（含 500ms 防抖 + 一轮 SSE + GET）。

具体数值待实测，但**必须显式承诺一个上界**，否则「同步了但不知道多久」无法验收。

### 14.4 移动端

- 冷启动先出骨架、再静默对账。
- 后台→前台用 seq 缺口检测，只补缺的会话。
- 实况通知与侧栏同源。

## 十五、风险与取舍

- **双写期风险**：迁移期间旧路径与新引擎可能同时写同一 store。规避：每期一个资源，迁移时旧写入点全部删除，不保留双写。
- **行为等价**：`replace-scope` 改变 `mergeStatusRefresh` 的语义（从只增不删改为整段替换）。需确认「有未回复 pending 的会话」不被误清 —— 沿用 `replaceServerStatus` 已有的保留逻辑（`activeSessionStore.ts:228`）。
- **复合 key 兼容**：`Scope` 不替换 `makeSessionKey`，避免全站破坏性改动；两者共存，`Scope` 内部复用同一约定。
- **messageStore 最后迁**：其内存裁剪、多前缀归并（`rawSessionToKey`）、流式合并逻辑复杂，先抽纯函数（已完成：`messagePartMerge.ts` / `messageToolSettle.ts`），再接入引擎。
- **不做巨型 store**：引擎不持有业务状态，只做调度与归约调用，避免成为新的耦合中心。
- **延迟不可消除（§11）**：后端跑在每台主机、无中央同步服务，跨端延迟由网络拓扑决定。设计目标是「滞后但收敛」，不是「零延迟」。若产品要求强实时一致，需要服务端参与（当前不具备），属于架构级变更，超出本设计范围。
- **无账号即无跨端**：B/C 类同步依赖 API Monitor 账号通道，未登录设备无法跨端共享偏好与已读水位。

| S1 | 心跳只在收到**真实事件**时重置；服务端空闲期只发 `: heartbeat` 注释帧（实测 **15s** 一次），SDK 解析器不 yield 注释帧 → 空闲会话 60s 后误判断连 | 订阅时传 SDK 的 `onActivity`（每 chunk 回调，含注释帧），新增 `touchConnection` / `isConnectionFresh`，把「连接还活着」与「有没有新事件」解耦 |
| S2 | SDK subscriber 队列满（4096）时抛错并**停掉整条连接**；旧代码按普通错误走指数退避 | 识别为背压：**立即重连**（不退避）、作废该服务器 seq 水位、通知上层标记整台会话 stale |
| S3 | durable `seq` 完全未使用，丢事件不可知 | 新增 `SeqGapTracker`：按 `(serverId, aggregateID)` 判定 `apply` / `duplicate` / `gap`；缺口事件丢弃并通知上层重拉快照，重拉后 `ackSeqGap` |

### 18.5 已评估、决定不做的三项

这三项曾在 §17 待决清单里，评估后确认**不需要做**。原判断基于推测而非代码，
这里按核实结果更正。

#### (1) 缺口检测的粒度成本 —— 不需要

原顾虑：所有 durable 事件都参与 seq 校验，活跃会话多时开销大。

核实：单次校验的开销是**一次字符串拼接 + 一次 Map 查询**
（`src/api/seqGap.ts:78-79`）。实测 durable 事件约 **48 条/分钟**
（554 条抓包里 48 条带 `durable`，跨 70 秒）。这个量级下不值得优化，
而且「只校验可见会话」会引入新问题：不可见会话的缺口检测不到，
用户切过去时数据已经错了。

真正需要处理的是**缺口触发后的重拉风暴**，已由 R3 的 300ms 合并窗口解决。

#### (2) ephemeral 事件丢失检测 —— 后果已被覆盖

原顾虑：`text.delta` / `status` / `usage.updated` 没有 seq，检测不到丢失。

核实 61 个 ephemeral 事件里，丢失有实际后果的只有三类，且都已有兜底：

| 事件 | 丢失后果 | 兜底 |
|---|---|---|
| `session.text.delta` / `reasoning.delta` | 正文少一段 | `session.text.ended`（**durable**）带完整全文并覆盖整个 part：`data: { assistantMessageID, ordinal, text: string }`，前端在 `api/v2/events.ts` 映射为 `MESSAGE_PART_UPDATED` 整体替换 |
| `session.status` / `session.idle` | 永久「生成中」 | R2：周期对账用 `/session/active` 驱动 `settleByAuthoritativeIdle` |
| `session.usage.updated` | token 数字停在旧值 | P3：`recordSessionUsageFallback` 取较大值 + 60s 对账 |

其余 `pty.*` / `mcp.*` / `config.updated` / `tui.*` 要么有其他通道（HTTP 轮询、
手动刷新），要么本就是瞬时信号（如 `tool.progress`，丢了只是进度条不动）。

结论：检测「哪个 delta 丢了」既无手段（无 seq），也无收益（`text.ended` 会覆盖）。

#### (3) 后端实例身份 —— 已实现，原描述有误

原文写「跨端水位键仍按前缀分」，**这与代码不符**：

```ts
// src/store/readWatermarkStore.ts:121-126
raise(sessionId: string, at: number) {
  const bareId = sessionKeyToSessionId(sessionId)   // 剥掉 serverId 前缀
  ...
  this.commit({ ...this.watermarks, [bareId]: at }) // 键是裸 sessionId
}
```

水位一直按**裸 sessionId** 存，多前缀（`local` / `aiagent:inst_x`）指向同一
后端时天然对齐——这正是文件头注释写明的设计意图。

剩余风险只有「两台不同后端生成相同裸 sessionId」。实测 id 形如
`ses_e78efd906ffe9XG9FgY3Mc8HoT`（30 字符、含时间戳与随机后缀），碰撞概率极低。
要彻底消除需服务端提供稳定实例标识，超出前端范围。

### 18.6 第三批（T1–T3）：未打开的会话丢事件后无法自愈

用户反馈：「前端有的信息没有及时刷新，只有 F5 后才正常，例如对话标题、有的回复」。

#### T1 缺口修复只覆盖「打开的会话」—— 已修

`useGlobalEvents` 的缺口修复（`flushGaps`）对每个 `aggregateID` 做三件事：
标 stale、通知打开该会话的 pane 重载、`ackSeqGap`。问题是**中间那一步在
没有 pane 时什么都不做**：

```ts
for (const consumer of sessionConsumers.values()) {
  if (consumer.sessionId !== scopedId) continue
  consumer.callbacks.onReconnected?.('network', serverId)   // 没人打开 → 循环体不执行
}
```

而缺口恰恰最常发生在「侧栏里有、但没打开」的会话上——它们同样在收事件。
结果：构成缺口的事件被丢弃（`checkSeqGap` 返回 true → `continue`），随后
`ackSeqGap` 把水位清掉，**没有任何人补拉**。那条会话的标题与最后回复就停在
断连那一刻，直到用户 F5（重建组件、重拉全量）才恢复。这与用户描述完全吻合。

修法：无 pane 时补一次会话元数据重拉（`getSession` 一个轻量 GET，带 TTL 缓存，
**不拉消息**），写回 `sessionListIndexStore`（侧栏列表）与 `activeSessionStore`
（session meta）。不拉消息是有意的：侧栏里可能同时有几十个会话报缺口，逐个拉
消息会打出一波大响应。

> 说明：这条修复的机理由代码直接可证（上面的 `for` 循环在无消费者时是空操作），
> 回归测试断言「无 pane 时仍会调用 `getSession`」。但**运行时端到端复现未成功**：
> 测试机用断网/断流制造的缺口，在「重连后第一次改名」这一窗口内，修复前后都能
> 正确显示新标题，无法稳定构造出「事件被丢弃且不恢复」的现场。因此本节结论的
> 强度是「机理成立 + 单测覆盖」，不是「已观测到 before/after 差异」。

#### T2 `onSessionStatus` 缺 directory 时项目行归不了类 —— 已修

项目折叠行靠 `buildFolderStatus(entry.directory, ...)` 把 busy 会话归到项目；
缺 directory 直接返回 `null`。而 `/api/session/active` 实测只返回
`{"ses_xxx":{"type":"running"}}`，**不带 directory**：

```
$ curl -s -u opencode:*** http://127.0.0.1:4096/api/session/active
{"data":{"ses_e78efd906ffe9XG9FgY3Mc8HoT":{"type":"running"}}}
```

directory 原本只在 `session.created` / `session.updated` 写入，存在「先 busy、
后 updated」的窗口。修法两处：`onSessionStatus` 缺目录时按需回查（已有则不发
请求）；乐观置忙时直接写入已知的 `input.directory` / `effectiveDirectory`。

> 说明：`/api/session/active` 不带 directory、以及 `buildFolderStatus` 缺 directory
> 返回 null，两点都已实测/单测证实。但「修好之后项目行确实会显示运行中」没有拿到
> 运行时证据：测试机的侧栏只渲染 `api-monitor-agent`（`/opt/api-monitor-agent`），
> 而测试会话属于别的目录，目标项目行根本不存在。此为未验证项。

#### T3 轮次结束后折叠块不自动收起 —— 已修并验证

`ChatArea.tsx` 中 `buildProcessTimeline` 的 `useMemo` 依赖漏了 `serverRunning`。
它参与 `isTurnSettled`（`if (serverRunning) return false`）：agent 跑完后服务端把
会话从 `/session/active` 摘掉、`serverRunning` 变 false，但 timeline 不重算 →
`isActive` 仍为 true → 折叠块不收起，只有刷新才收起。

运行时证据（真实环境，未刷新页面）：

```
[+6s]  ... | Working for 5s shell 1 steps
[+8s]  ... | Working for 7s
[+11s] ... | Working for 10s
[+14s] Worked for 12s 11 steps      ← 自动收起
```

#### 已评估但**未采纳**的两项（避免下次重复踩）

1. **让 `SeqGapTracker` 在跳号时推进水位 / 放宽丢弃条件**。曾按「无害缺口
   直接放行」实现（含 `prev` 字段、`isGapHarmless`、事件类型记忆），实现后
   `events.test.ts` 有 4 条断言失败——它们验证的正是刻意设计的行为（缺口事件
   必须丢弃、ack 前不得推进水位、缺口回调抛错不影响事件流）。已全部回滚。
   教训：丢弃是刻意的安全语义，缺口期间数据本来不可信；要做的是**补上修复
   通道**（T1），不是放宽检测。

2. **`onReconnected` 的 cooldown 改为延后补发**。代码上确实存在「2s 窗口内的
   第二次重连通知被直接 `return` 丢弃」的问题。但写不出能区分修复与否的测试：
   连接流立即结束时重连会持续发生，cooldown 自然过期，测试对「删掉修复」仍然
   通过（假阳性）。按「没有可验证证据就不提交」的原则放弃该改动。
